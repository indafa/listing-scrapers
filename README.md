# جمع‌آوری آگهی‌های بازار اصفهان

این ریپو بخش «سنگین» سیستم مشاور فروشگاه موبایل است و روی **GitHub Actions** اجرا می‌شود. کارش فقط
جمع‌کردن و غنی‌سازی **آگهی‌های عمومی** است؛ هیچ داده‌ی مشتری، کلید هوش مصنوعی یا توکن ربات در این ریپو
نیست و هیچ هوش مصنوعی‌ای در آن اجرا نمی‌شود. نتیجه‌ی همه‌ی کارها در پایگاه داده‌ی D1 همان سیستم نوشته می‌شود.

## کارها

هر کار یک ورک‌فلو دارد که **فقط** با `workflow_dispatch` اجرا می‌شود. زمان‌بندی را Worker مشاور انجام می‌دهد
(با API گیت‌هاب)؛ دکمه‌ی **Run workflow** در تب Actions هم برای اجرای دستی کار می‌کند.

| ورک‌فلو | فایل اجرا | چه می‌کند | برنامه‌ی پیشنهادی |
|---|---|---|---|
| `collect.yml` | `categories/mobile-tablet/run.mjs` | آگهی‌های تازه‌ی موبایل و تبلت را از منبع می‌خواند و در `listings` می‌نویسد. ورودی اختیاری: `city_id` | هر ۱۰ دقیقه |
| `enrich.yml` | `jobs/enrich.mjs` | ویژگی‌های دست‌دوم (باتری، تعمیر، پرچم‌ها، امتیاز وضعیت) را استخراج و آگهی را به کاتالوگ وصل می‌کند | هر ۳۰ دقیقه |
| `liveness.yml` | `jobs/liveness.mjs` | آگهی‌های ۷۲ ساعت اخیر را دوباره می‌گیرد (حداکثر ~۱۵۰ درخواست) و فعال/بسته‌بودنشان را ثبت می‌کند | هر ساعت |
| `prices.yml` | `jobs/prices.mjs` | میانگین قیمت ۷۲ ساعت اخیر را با حذف داده‌ی پرت می‌سازد (وضعیت `pending` تا تایید مدیر) | روزانه |
| `catalog.yml` | `jobs/catalog.mjs` | کاتالوگ مدل‌ها را از نام مدل‌های دیده‌شده می‌سازد/به‌روز می‌کند | روزانه |
| `news.yml` | `jobs/news.mjs` | خبرهای فید RSS تنظیم‌شده در پنل را خام ذخیره می‌کند (پیش‌فرض خاموش) | هفتگی |

## تنظیمات لازم

مسیر: **Settings ← Secrets and variables ← Actions**. مقدار واقعی هیچ‌کدام در این ریپو نوشته نمی‌شود.

**Secrets** (تب Secrets):

| نام | چیست |
|---|---|
| `CF_ACCOUNT_ID` | شناسه‌ی حساب کلودفلر |
| `CF_API_TOKEN` | توکن API کلودفلر؛ فقط دسترسی **ویرایش D1** (Edit) |
| `CF_D1_DATABASE_ID` | شناسه‌ی پایگاه داده‌ی D1 (`mobile-advisor-db`) |

**Variables** (تب Variables):

| نام | چیست |
|---|---|
| `SOURCE_SEARCH_URL` | آدرس جست‌وجوی منبع آگهی (آدرس کامل، با https) |
| `SOURCE_DETAIL_URL_BASE` | پیشوند آدرس جزئیات آگهی؛ توکن آگهی بعد از آن افزوده می‌شود |
| `SOURCE_LINK_BASE` | پیشوند لینک عمومی آگهی؛ توکن آگهی بعد از آن افزوده می‌شود |
| `SOURCE_CITY_ID` | شماره‌ی شهر در منبع (اصفهان = `4`) |
| `SOURCE_CITY_NAME` | نام شهر (`اصفهان`) |
| `CATALOG_SOURCE_BASE` | اختیاری: آدرس فهرست مدل‌های خارجی (JSON یا متن ساده)؛ خالی = خاموش |

هیچ آدرسی در کد نیست؛ اگر یکی از متغیرها خالی باشد، لاگ همان نام را می‌گوید.

## قرارداد داده با Worker

- `listing_features.match_method`: `auto` (تطبیق قطعی)، `verify` (۰٫۶ تا ۰٫۸۵، منتظر تطبیق با AI در Worker)،
  `unmatched` (زیر ۰٫۶). Worker مقدارهای `ai` و `admin` را می‌نویسد و این ریپو آن‌ها را بازنویسی نمی‌کند.
- `unmatched_queue`: هر متن یکتا یک ردیف (`open` یا `verify`)؛ `verify`ِ حل‌نشده بعد از ۲۴ ساعت `open` می‌شود.
- `market_price_daily`: ردیف‌ها `pending` نوشته می‌شوند؛ `flagged=1` یعنی نمونه‌ی کمتر از ۵ یا جهش بیش از ۱۵٪.
  کلید ناشناخته: حافظه `0` و رنگ `''`. ردیفی که تصمیم‌گیری شده باشد دوباره نوشته نمی‌شود.
- `listing_state`: `is_active`، `checked_at`، `closed_reason`، `last_price`.
- منطق تطبیق و آمار از `shared/core/core.mjs` می‌آید؛ آن فایل **خودکار ساخته می‌شود** و دستی ویرایش نمی‌شود.

## رفتار مهم موتور جمع‌آوری (`shared/runner.mjs`)

- فقط صفحه‌ی اول نتایج (تازه‌ترین‌ها) گرفته می‌شود؛ فاصله‌ی درخواست‌ها ۱٫۲ ثانیه.
- آگهی بی‌تغییری که کمتر از ۶۰ دقیقه پیش دیده شده دوباره در D1 نوشته نمی‌شود (سقف نوشتن روزانه‌ی پلن رایگان).
- در حالت «بدون گیرنده» (`recipients/empty.json`) فقط جمع‌آوری انجام می‌شود و آگهی هیچ‌وقت «نیازمند ارسال» حساب نمی‌شود.
- ساختار جدول `listings` در شروع هر اجرا چک می‌شود؛ ناهماهنگی با پیام روشن اجرا را متوقف می‌کند.
- اگر همه‌ی شاخه‌ها بی‌نتیجه بمانند، اجرا قرمز می‌شود تا گیت‌هاب خبر بدهد.

## اجرای تست‌ها

```bash
npm test
```

تست‌ها فقط به `node:test` و `node:sqlite` نیاز دارند (Node نسخه‌ی ۲۲٫۵ یا بالاتر)، بدون هیچ وابستگی و بدون اینترنت.
خود کارها (ورک‌فلوها) با Node 20 اجرا می‌شوند.
